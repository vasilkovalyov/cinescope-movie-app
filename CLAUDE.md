# CineScope — project rules for AI agents

CineScope is a Next.js 16 (App Router) movie/TV browsing site backed by the TMDB API. See `docs/architecture.md` for the full architectural writeup. This file lists only the rules and gotchas an agent needs to avoid breaking things or repeating discovery work.

## Next.js 16 API changes (do not use your training-data defaults)

This repo runs `next@16.3.0`, which changed some App Router conventions from what most training data assumes. Bundled docs live in `node_modules/next/dist/docs/` — read them for anything App Router related before writing code, per the block generated by `next dev` at the top of `AGENTS.md`.

- `error.tsx` / `global-error.tsx` receive a **`retry`** prop, not `reset`. See `app/error.tsx` for the current usage: `({ error, retry }: { error: Error & { digest?: string }; retry: () => void })`.
- `params`/`searchParams`/`layout` props should use the global `PageProps<'/route'>` / `LayoutProps<'/route'>` helpers (auto-generated by `next dev`/`next build`, no import needed) instead of hand-written `Promise<{ ... }>` prop types. `app/layout.tsx` already does this (`LayoutProps<'/'>`).

## Routing reality vs. constants

Only `/` (`app/page.tsx`) exists today. `src/constants/pages.constant.ts` (`PAGES`) already defines routes that have **no corresponding `app/` folder yet**: `/movies`, `/movie`, `/tv-shows`, `/people`, `/person`, `/search`, `/discover`. Header/footer nav and card links point at these paths intentionally (this is a WIP site skeleton) — don't treat 404s on those links as bugs to silently "fix" by deleting the links.

Note the singular/plural convention: `PAGES.movie` / `PAGES.person` are **detail-route prefixes** (`/movie/{id}`, `/person/{id}`); `PAGES.movies` / `PAGES.people` are **list/browse routes**. Keep this distinction when adding new pages or links.

## Data fetching & API layer

- TMDB access is **plain async functions**, not classes — `src/api/movies.ts`, `src/api/tv-series.ts`, `src/api/people.ts` each export functions built on `fetchGetApiTMDB` (`src/api/fetch-api-tmdb.ts`). The **only class left in the API layer is `GenresApi`** (`src/api/genres.ts`): a static async factory (`GenresApi.create('movie' | 'tv')`) with a private constructor, needed because building the genre dictionary requires an awaited fetch before you have anything to construct. Don't reintroduce classes for `movies`/`tv-series`/`people` — that was tried and reverted (see below).
- There are **no Next.js Route Handlers** (`app/api/**/route.ts`) — Server Components call these functions directly (see `app/page.tsx` and the `Block*`/`Section*` components it renders). `TMDB_API_TOKEN` (in `.env`, server-only) is read inside `fetchGetApiTMDB`. Never call these functions from a Client Component — the token isn't exposed to the client on purpose.
- Functions that need to resolve `genre_ids` → `genres` take a **`genres: GenresDictionary` parameter explicitly** (`getTrendingList(genres)`, `getUpcomingList(genres)`, `getPopularList(genres)`, `getNowPlayingList(genres)`, `getTopRatedList(genres, params?)`, `getMovieEditorPick(genres)` — all in `src/api/movies.ts`). Get the dictionary once per request via `await GenresApi.create('movie')`, then pass `.allGenres` down as a plain value — don't call `GenresApi.create` more than once per page. Movie detail-fetchers (`getPopularMovieDetails`, `getMovieFullDetails`, `getMovieHomeHeroDetails`) do **not** take `genres` — TMDB's `/movie/{id}` endpoint already returns resolved `genres: MovieGenre[]`, so there's nothing to map.
- **Name collisions in the `@/api` barrel**: `movies.ts`, `tv-series.ts`, and `people.ts` each export a function called `getPopularList`, and `movies.ts`/`tv-series.ts` both export `getTopRatedList`. `src/api/index.ts` keeps the movie versions under their bare names and renames the others on re-export: `getPopularList as getPopularTVSeriesList` / `getTopRatedList as getTopRatedTVSeriesList` (from `tv-series.ts`), `getPopularList as getPeoplePopularList` (from `people.ts`). `import { getPopularList } from '@/api'` always gets the **movie** function — use the renamed TV/people exports for those domains. Follow the same rename-on-export convention if you add another same-named function to a non-movie API module.
- `@tanstack/react-query` and `TanStackProvider` (`src/providers/tanstack-provider.tsx`) are installed but **not mounted anywhere** (not in `app/layout.tsx`/`BaseLayout`). Don't assume React Query is wired up client-side; if you need client-side caching you must mount the provider first.
- Raw TMDB shapes (`Movie`, `TVSeries`, `People`, `*Details` types in `src/types/`) are never passed straight into UI components. They go through `src/utils/adapters/*` first, which reshape them into the `*Props` types the components in `src/components/common` and `src/components/sections` expect. Follow this pattern for new sections: add an adapter rather than reshaping data inline in a page/component.

## Section composition: self-fetching "blocks" vs. pure sections

`app/page.tsx` does not fetch data for every section anymore. Each TMDB-backed preview row on the home page is its own small async Server Component in `src/components/sections/`, named `Block*` (`BlockTrendingNow`, `BlockPopularMovies`, `BlockNowPlaying`, `BlockTopRatedFilms`, `BlockComingSoon`, `BlockPopularTVShows`, `BlockTopRatedSeries`, `BlockNotablePeople`). Each one calls the matching `src/api/*` function itself, adapts the result, and renders a `SectionListPreview`. Movie-backed blocks take `genres: GenresDictionary` as a prop (fetched once in `page.tsx` via `GenresApi.create('movie')` and threaded down); TV/people-backed blocks take no props. **When adding a new home-page preview row, add a new `block-*.tsx` following this pattern — don't add another inline fetch + adapter call in `app/page.tsx`.**

`SectionEditorPickBanner` (`src/components/sections/section-editor-pick-banner/`) follows the same self-fetching pattern even though it's named `Section*`: it takes only `{ genres }`, calls `getMovieEditorPick(genres)` itself, and renders `undefined` when there's no pick. **`Section*` naming is not a reliable signal for "pure/presentational"** — `SectionHomeHero`, `SectionTopRatedMovies`, and `SectionListPreview` *are* pure (they take already-adapted `*Props` and fetch nothing); `SectionEditorPickBanner` is not. Check a component's prop type before assuming which kind it is.

`app/page.tsx` itself now only awaits two calls directly (`getPopularMovieDetails` for the hero, `getTopRatedList(genres, { topSize: TOP_RATE_COUNT })` for the top-rated banner) before returning JSX — the rest happens inside the block/section components it renders, so those fetches are no longer forced into one long sequential `await` chain in `Home`. If you add more direct `await`s to `Home` itself, prefer `Promise.all` for anything independent rather than reintroducing a sequential chain.

## Styling

- Tailwind v4, CSS-first config — there is **no `tailwind.config.ts`**. Theme tokens (colors, fonts) are defined as CSS variables in `app/globals.css` under `:root` and mapped via `@theme inline`. Add new design tokens there, not in a JS config.
- shadcn/ui is configured with `"style": "radix-nova"` and `"rsc": false` (`components.json`); it imports a prebuilt `shadcn/tailwind.css` from the `shadcn` npm package in `globals.css`. Generated primitives live in `src/components/ui/` — treat these as shadcn-generated and prefer regenerating/extending via shadcn conventions over hand-editing internals.
- Use the `cn()` helper (`src/lib/utils.ts`, clsx + tailwind-merge) for conditional classes, matching existing components.

## Known dead code / duplicated dependencies (don't extend these, and be aware when refactoring)

- Two carousel libraries are installed: `swiper` (actively used via `src/components/common/swiper-carousel.tsx`) and `embla-carousel-react` (only used by the shadcn-generated `src/components/ui/carousel.tsx`, which is **not exported** from `src/components/ui/index.ts` and not used anywhere). New carousels should use `SwiperCarousel`, matching the rest of the app.
- `src/features/favorite-toggler.tsx` (`FavoriteToggler`) renders a `Toggle` with no persisted state, store, or API call behind it — favoriting is UI-only right now.

## Type-system gotchas

- Several TMDB-derived types include a `softcore` field (`Movie`, `MovieDetails`, `TVSeries`, `TVSeriesDetails`, `People`/`PersonKnownFor`). This is **not a real TMDB API field** and isn't read anywhere in the codebase — don't rely on it being populated from a real API response.
- `TVSeriesDetails.id` is typed `string`, while `Movie.id`/`TVSeries.id` are typed `number`. TMDB actually returns numeric ids for TV series too. Watch for this mismatch if you touch TV series code.
- `PreviewMovieCardProps.id` is `string` but `PreviewPersonCardProps.id` is `number` — intentional inconsistency between the two card types, not a typo to "fix" without checking both call sites.
- `src/components/sections/section-editor-pick-banner/section-editor-pick-banner.type.ts` declares **two** differently-shaped types: `SectionEditorPickBannerProps` (`{ genres: GenresDictionary }`, the fetch-component's own props) and `EditorPickBannerProps` (the fully-adapted presentational shape, produced by `editorSectionPickBannerAdapter`). Don't conflate them — the names are easy to mix up.

## Conventions

- File naming is kebab-case; multi-file components live in their own folder with `<name>.tsx`, `<name>.type.ts`, and a barrel `index.ts` (e.g. `src/components/common/preview-movie-card/`). Follow this for new multi-file components; single-file components (e.g. `src/components/common/logo.tsx`) don't need a folder.
- Barrel files (`index.ts`) re-export the public surface of each folder (`api`, `components/common`, `components/ui`, `components/sections`, `constants`, `types/movie`, `utils`, `utils/adapters`, `features`). Import from the barrel (`@/components/common`), not the deep path, unless the barrel doesn't export what you need.
- Path aliases: `@/*` → `src/*` (used everywhere). `@components/*` → `src/components/*` is also declared in `tsconfig.json` but not actually used anywhere in the codebase — prefer `@/components/*` for consistency with existing code.
- Prettier auto-sorts imports into groups (react → next → third-party → `@/components` → `@/hooks` → `@/store` → `@/services` → `@/config`/`@/constants` → `@/i18n` → `@/types` → `@/utils` → relative). Run `npm run format` rather than hand-ordering imports.
- ESLint enforces `eqeqeq` (smart), `max-depth: 4`, `max-params: 5`, `@typescript-eslint/no-shadow`, and self-closing components. `tsconfig.json` has `noUncheckedIndexedAccess` and `noUnusedLocals`/`noUnusedParameters` on — array/object index access is `T | undefined`, and unused vars/params will fail the build.
