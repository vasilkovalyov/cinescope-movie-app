# CineScope Architecture

CineScope is a Next.js 16 App Router site that renders a movie/TV/people browsing experience sourced from The Movie Database (TMDB) API. It is an early-stage project (8 commits at the time of writing): only the home page (`/`) is implemented; every other route referenced by navigation and card links is a planned route that does not exist yet.

This document goes deeper than `CLAUDE.md` — read `CLAUDE.md` first for the condensed rules, and come here when you need the full picture of how a layer works or why it's shaped the way it is.

## 1. Runtime & tooling

- **Next.js 16.3.0**, App Router only (no `pages/` directory). React 19.2.8.
- **This Next.js version has App Router changes not reflected in most training data.** The repo's `AGENTS.md` (imported by `CLAUDE.md` via `@AGENTS.md`) is a block regenerated by `next dev` that instructs agents to consult `node_modules/next/dist/docs/` before writing App Router code. Two changes already visible in this codebase:
  - `error.tsx`/`global-error.tsx` boundary components receive a `retry()` callback, not `reset()` (see `app/error.tsx`).
  - `PageProps<'/route'>` and `LayoutProps<'/route'>` are ambient/global helper types (generated during `next dev`/`next build`/`next typegen`) that infer `params`/`searchParams`/named slots from the route's actual file-system location, replacing hand-written `{ params: Promise<{...}> }` prop types. `app/layout.tsx` uses `LayoutProps<'/'>`.
- **TypeScript**: strict mode plus `noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `forceConsistentCasingInFileNames`. Path aliases in `tsconfig.json`: `@/*` → `src/*` (used throughout) and `@components/*` → `src/components/*` (declared but never actually used — everything imports via `@/components/...`).
- **Styling**: Tailwind CSS v4 in CSS-first mode — there is no `tailwind.config.ts`/`.js` anywhere. All theme configuration lives in `app/globals.css`.
- **Linting/formatting**: ESLint 9 flat config (`eslint.config.mjs`) built on `eslint-config-next` + `typescript-eslint` + `eslint-plugin-react-hooks`, with Prettier run through `eslint-plugin-prettier`/`eslint-config-prettier`. Prettier (`.prettierrc`) uses `@trivago/prettier-plugin-sort-imports` with an explicit `importOrder` group list (react/next → third-party → `@/components` → `@/hooks` → `@/store` → `@/services` → `@/config`|`@/constants` → `@/i18n` → `@/types` → `@/utils` → relative `.`). Several of those groups (`@/hooks`, `@/store`, `@/services`, `@/i18n`) don't exist yet in the codebase — the import-order config is ahead of the current folder structure, presumably anticipating future additions.
- No test runner is configured (no Jest/Vitest/Playwright config, despite `vitest.config.ts` being listed in `tsconfig.json`'s `include` — that's a leftover from the Next.js template, not a real file in this repo).

## 3. Rendering model: Server vs. Client Components

The default is a Server Component; `'use client'` is added only where interactivity is required. As of this writing, the client boundary is pushed down to leaf components:

- **Server Components** (no directive): `app/layout.tsx`, `app/page.tsx`, `app/not-found.tsx`, all of `src/components/sections/*` except where noted, `src/components/common/*` presentational components (`Logo`, `Rating`, `GenreList`, `MovieMeta`, banner/card components), `src/components/layouts/base-layout.tsx`, `footer.tsx`, `header.tsx`.
- **Client Components** (`'use client'`): anything with local state, browser APIs, or event handlers —
  - `app/error.tsx` (error boundaries must be client components; uses `useEffect` to log).
  - `src/providers/tanstack-provider.tsx` (holds `QueryClient` in `useState`).
  - `src/components/layouts/header/components/header-sticky-wrapper.tsx` (scroll listener via `useEffect`).
  - `src/components/layouts/header/components/header-navigation.tsx` (`usePathname()` for active-link styling) and `header-mobile-menu.tsx` (open/close state).
  - `src/components/common/movie-trailer-toggler.tsx` (dialog open state) and `swiper-carousel.tsx` (Swiper needs the DOM).
  - `src/features/favorite-toggler.tsx` (interactive toggle, currently stateless beyond the underlying `Toggle` primitive).
  - Most `src/components/ui/*` primitives that wrap Radix (Dialog, Select, Tabs, etc.) are client components internally, consistent with `components.json`'s `"rsc": false` shadcn setting.

`SectionHomeHero`, `SectionListPreview`, `SectionTopRatedMovies`, `SectionEditorPickBanner`, `BannerRatedMovie`, `PreviewMovieCard`, `PreviewPersonCard`, and every `Block*` component are themselves Server Components that _render_ client children (`MovieTrailerToggler`, `SwiperCarousel`, `FavoriteToggler`) — a standard "server component composes client leaf" pattern. When adding new interactive UI, keep the interactive part as small and as low in the tree as possible rather than promoting a whole section to `'use client'`.

## 4. Data fetching & the API layer

There are no Next.js Route Handlers (`app/api/**/route.ts`) in this project. All data comes from TMDB, fetched directly inside async Server Components at request/build time.

### 4.1 `fetchGetApiTMDB` (`src/api/fetch-api-tmdb.ts`)

A single generic fetch wrapper: builds a query string from a params object (dropping `undefined` values), calls `${MOVIE_API_URL}${url}`, sends `Authorization: Bearer ${process.env.TMDB_API_TOKEN}`, throws on non-OK responses, and returns `response.json()` cast to the generic `T`. `TMDB_API_TOKEN` is read straight from `process.env` inside this function — it is never passed through `NEXT_PUBLIC_*`, so it stays server-only. Any code path that calls into `src/api/*` must therefore stay server-side (Server Component, or a future Route Handler/Server Action) — never import these functions into a `'use client'` file.

### 4.2 API modules (`src/api/*.ts`)

The API layer used to be three classes (`MoviesApi`, `TVSeriesApi`, `PeopleApi`) constructed with an injected genre dictionary. It was refactored to plain exported functions — see "Why the class-based design was dropped" below. Current shape:

- `GenresApi` (`src/api/genres.ts`) — the **only class left**. Static async factory (`GenresApi.create('movie' | 'tv')`) that fetches the genre list once and exposes it as a `ReadonlyMap<number, string>` (`GenresDictionary`) via the `.allGenres` getter. The constructor is private; you must go through `.create()`. This one stays a class because building the dictionary requires an `await` before there's anything to expose — a plain function returning the dictionary would work just as well and would be a reasonable simplification, but as of now the static-factory shape is what's implemented.
- `src/api/movies.ts` — plain async functions: `getTrendingList(genres)`, `getUpcomingList(genres)`, `getTopRatedList(genres, params?)`, `getPopularList(genres)`, `getNowPlayingList(genres)`, `getMovieEditorPick(genres)` all take the `GenresDictionary` as an explicit first argument and map TMDB's `genre_ids: number[]` to resolved `genres: MovieGenre[]` via a local `getFormattedMoviesGenres` helper; list functions truncate via `limitArray` (default `PREVIEW_LIST_COUNT = 10`). `getPopularMovieDetails(params)`, `getMovieFullDetails(movieId, params?)`, `getMovieHomeHeroDetails(movieId, params?)` take **no** `genres` argument — TMDB's `/movie/{id}` endpoint returns fully resolved `genres: MovieGenre[]` already, so there's nothing to map. `getPopularMovieDetails` fetches the current popular list, takes the first result, and calls `getMovieHomeHeroDetails` on its id.
- `src/api/tv-series.ts` — plain functions `getTopRatedList(params?)`, `getPopularList(params?)`, `getTVSeriesLimitedDetails(movieId, params?)`. No genre dependency (TV series objects already carry resolved `genres`). `getTopRatedList`/`getPopularList` each fetch a list, then `Promise.all` a per-item details call to attach credits — this is the one place in the API layer that already parallelizes independent requests.
- `src/api/people.ts` — single function `getPopularList()`.
- `getRegion()` (`src/utils/region.ts`) reads the `accept-language` header via `next/headers` `headers()` and derives an `Intl.Locale` region, used to regionalize "now playing"/"upcoming"/"editor's pick" queries.

**Barrel re-exports and name collisions**: `movies.ts`, `tv-series.ts`, and `people.ts` each define a `getPopularList`, and `movies.ts`/`tv-series.ts` both define `getTopRatedList`. `src/api/index.ts` re-exports the movie versions under their bare names and renames the others: `getPopularList as getPopularTVSeriesList` / `getTopRatedList as getTopRatedTVSeriesList` from `tv-series.ts`, `getPopularList as getPeoplePopularList` from `people.ts`. Anything imported as `{ getPopularList }` or `{ getTopRatedList }` from `@/api` is always the movie version.

**Why the class-based design was dropped**: `MoviesApi` used to be constructed as `new MoviesApi({ genres })` and called as `movieApi.getPopularList()`, etc. Two problems motivated the change to plain functions with an explicit `genres` parameter: (1) three of the class's methods (the detail-fetchers) never touched the injected `genres`, so the class implied more shared state/cohesion than actually existed; (2) `getTrendingList` existed both as an instance method (using `this._genres`) _and_ as a duplicate standalone function with the same body (using a `genres` parameter) — a sign the class/function boundary wasn't being applied consistently. The current design has exactly one implementation per operation, and every function's signature makes its actual data dependency (or lack of one) explicit. `TVSeriesApi`/`PeopleApi` never had meaningful constructor state to begin with, so they collapsed to plain functions with no `genres`-style tradeoff at all.

### 4.3 Home page composition (`app/page.tsx`) and section "blocks"

`Home` no longer fetches data for every section itself. It: awaits `GenresApi.create('movie')` once and keeps the resulting `genres: GenresDictionary` as a plain value; awaits `getPopularMovieDetails({ includes: ['credits', 'videos'] })` for the hero and `getTopRatedList(genres, { topSize: TOP_RATE_COUNT })` for the top-rated carousel; adapts both and renders `SectionHomeHero`/`SectionTopRatedMovies`; then renders a flat list of self-fetching components, passing `genres` to the ones that need it:

```tsx
<SectionHomeHero {...popularMovieHomeHeroAdapter(popularMovie)} />
<SectionTopRatedMovies items={topRatedMoviesAdapter(topRatedMovies.results)} />
<BlockTrendingNow genres={genres} />
<BlockPopularMovies genres={genres} />
<BlockNowPlaying genres={genres} />
<SectionEditorPickBanner genres={genres} />
<BlockTopRatedFilms genres={genres} />
<BlockComingSoon genres={genres} />
<BlockPopularTVShows />
<BlockTopRatedSeries />
<BlockNotablePeople />
```

Every `Block*` component (`src/components/sections/block-*.tsx`) is a small `async` Server Component that owns one TMDB call, one adapter call, and renders one `SectionListPreview`:

| Component             | Calls                                                                      | Needs `genres`? |
| --------------------- | -------------------------------------------------------------------------- | --------------- |
| `BlockTrendingNow`    | `getTrendingList(genres)`                                                  | yes             |
| `BlockPopularMovies`  | `getPopularList(genres)`                                                   | yes             |
| `BlockNowPlaying`     | `getNowPlayingList(genres)`                                                | yes             |
| `BlockTopRatedFilms`  | `getTopRatedList(genres)` (no `topSize` — default `limitArray` truncation) | yes             |
| `BlockComingSoon`     | `getUpcomingList(genres)`                                                  | yes             |
| `BlockPopularTVShows` | `getPopularTVSeriesList()`                                                 | no              |
| `BlockTopRatedSeries` | `getTopRatedTVSeriesList()`                                                | no              |
| `BlockNotablePeople`  | `getPeoplePopularList()`                                                   | no              |

`SectionEditorPickBanner` (see §6) follows the same self-fetching shape but is named `Section*`, not `Block*`, and is not a `SectionListPreview` wrapper — it renders its own bespoke banner markup.

**Performance note**: previously `Home` awaited all ~11 of these calls sequentially inside one function body, so the page's TTFB was the sum of every request's latency. Now only 2 calls are awaited directly in `Home` (still back-to-back, not `Promise.all`ed); the rest live inside sibling `async` Server Components rendered directly in JSX rather than awaited up front, so their fetches are no longer forced into a single sequential chain in the page function. This is a real improvement, though it's an emergent effect of the component split rather than an explicit streaming/`Suspense` setup — there's no `<Suspense>` boundary anywhere in the tree yet, so the page as a whole still doesn't start streaming to the client until every block has resolved server-side.

Note `getTopRatedList` is still called twice per page load with different arguments (`{ topSize: TOP_RATE_COUNT }` for the hero-adjacent carousel in `Home`, no `params` for `BlockTopRatedFilms`'s preview row) — intentional (different result sizes), but it does mean the top-rated endpoint is hit twice.

## 5. Types and adapters — the view-model boundary

`src/types/` mirrors TMDB's actual JSON shapes as closely as the codebase needs (e.g. `Movie`, `TVSeries`, `People`, and the parameterized `MovieDetails<Credits, Videos, Images, Keywords>` / `TVSeriesDetails<...>` generics that use `AppendField<Key, T>` (`src/types/utils.type.ts`) to conditionally add `credits`/`videos`/`images`/`keywords` keys depending on what `append_to_response` was requested for). `MovieHomeHeroDetails` and `MovieFullDetails` are two different instantiations of `MovieDetails` with different append-field combinations; `TVSeriesLimitedDetails`/`TVSeriesFullDetails` mirror this for TV.

Components never receive these raw API types directly. Instead, `src/utils/adapters/*` contains pure mapping functions that convert API types into the exact prop shapes the presentational components declare in their own `*.type.ts` files:

- `popular-movie.adapter.ts` → `popularMovieHomeHeroAdapter(MovieHomeHeroDetails) => SectionHeroLargeProps` (formats runtime, rounds rating, resolves director from `credits.crew`, extracts trailer URL from `videos.results`).
- `top-rated-movies.adapter.ts` → `topRatedMoviesAdapter(MovieResolved[]) => BannerRatedMovieProps[]`.
- `list-preview.adapter.ts` → `listMoviesPreviewAdapter`, `listTVSeriesPreviewAdapter`, `listPeoplePreviewAdapter`, each producing `PreviewMovieCardProps[]`/`PreviewPersonCardProps[]`.
- `editor-pick-banner.adapter.ts` → `editorSectionPickBannerAdapter(MovieResolved) => EditorPickBannerProps`. Note `EditorPickBannerProps` is defined in and imported from `@/components/sections` (specifically `section-editor-pick-banner.type.ts`), not `@/components/common` — the presentational banner markup now lives inside `SectionEditorPickBanner` itself rather than a separate `components/common` component.

**When adding a new section that consumes TMDB data, add a new adapter rather than shaping the API response inline inside the component or the page.** This keeps components decoupled from TMDB's actual field names (`backdrop_path`, `vote_average`, `genre_ids`, etc.) and centralizes formatting helpers (`getFormatRuntime`, `getImageFullUrl`, `roundToDecimal`, `getTrailerUrl`, `getEditorPickMovie`, `getRatingColor`, `limitArray` — all in `src/utils/common.ts`, re-exported via `src/utils/index.ts`).

### Known type inconsistencies

- `Movie`, `MovieDetails`, `TVSeries`, `TVSeriesDetails`, `People`/`PersonKnownFor` all declare a `softcore: boolean | string` field. This is not part of TMDB's actual API response and is never read anywhere in the codebase — treat it as noise, not a real content-rating flag, unless it's deliberately wired up to something later.
- `TVSeriesDetails.id` is typed `string`; `Movie.id` and `TVSeries.id` are typed `number`. TMDB's actual `id` for TV series is numeric, so this is a latent type bug — code that does `tvSeries.id.toString()` (e.g. `listTVSeriesPreviewAdapter`) happens to still work at runtime (since `.toString()` on a string is a no-op) but the type doesn't reflect reality.
- `PreviewMovieCardProps.id: string` vs. `PreviewPersonCardProps.id: number` — an existing, apparently intentional inconsistency between the two card prop types (movie ids get stringified early via `id.toString()` in the adapter; person ids are passed through as `number`). Don't "fix" one without checking both `SectionListPreview` branches and all callers.
- `section-editor-pick-banner.type.ts` defines two similarly-named but distinct types: `SectionEditorPickBannerProps` (`{ genres: GenresDictionary }` — what the self-fetching `SectionEditorPickBanner` component takes as props) and `EditorPickBannerProps` (the fully-adapted presentational shape produced by `editorSectionPickBannerAdapter` and used internally to render the banner). Easy to reach for the wrong one when editing this component.

## 6. Component architecture & naming

- **`components/ui/`** — shadcn/ui-generated primitives (`components.json`: `style: "radix-nova"`, `rsc: false`, `iconLibrary: "lucide"`, base color `neutral`, CSS variables on). Built on `radix-ui` + `class-variance-authority` (`cva`) for variants + `cn()` for merging. Treat these as generated code: extend via variants/props rather than editing internals where possible, and regenerate through shadcn tooling for new primitives.
- **`components/common/`** — small reusable presentational pieces (`Logo`, `Rating`, `GenreList`, `MovieMeta`, `SwiperCarousel`, `MovieTrailerToggler`) plus card/banner components that model a specific TMDB-derived shape (`PreviewMovieCard`, `PreviewPersonCard`, `BannerRatedMovie`). All re-exported from `src/components/common/index.ts`. There is no `EditorPickBanner` here anymore — it was moved into `components/sections` (see below) and turned into a self-fetching component.
- **`components/sections/`** — two different kinds of components live here, and the `Section*`/`Block*` naming only partially tells you which is which:
  - **Pure/presentational** (`SectionHomeHero`, `SectionTopRatedMovies`, `SectionListPreview`) — receive already-adapted `*Props` from a caller, fetch nothing themselves. `SectionListPreview` is polymorphic over a discriminated union (`type: 'movie' | 'person'`) that changes both the expected `items` shape and which card component renders.
  - **Self-fetching** (`SectionEditorPickBanner`, and every `BlockTrendingNow` / `BlockPopularMovies` / `BlockNowPlaying` / `BlockTopRatedFilms` / `BlockComingSoon` / `BlockPopularTVShows` / `BlockTopRatedSeries` / `BlockNotablePeople`) — `async` Server Components that take only raw inputs (`{ genres }` or nothing), call an `@/api` function themselves, adapt the result, and render. `SectionEditorPickBanner` renders its own bespoke markup; the `Block*` components each render a `SectionListPreview`. See §4.3 for the full breakdown of which block calls what.

  When adding a new home-page section backed by TMDB data, follow the self-fetching pattern (new `block-*.tsx`, or extend `SectionEditorPickBanner`'s approach for something that isn't a `SectionListPreview`) rather than fetching in `app/page.tsx` and passing props down.

- **`components/layouts/`** — site chrome: `BaseLayout` (wraps `Header` + `main` + `Footer`), `Header` (composes `HeaderStickyWrapper` + `HeaderNavigation` + `HeaderMobileMenu`, colocated under `header/components/`), `Footer` (hardcodes its own nav column data inline rather than reusing `HEADER_NAVIGATION`).
- **`features/`** — components with actual interactive behavior beyond simple UI state (currently just `FavoriteToggler`, which wraps the `Toggle` primitive with no persistence layer behind it yet — favoriting doesn't do anything beyond visual toggle state today).

**File/folder convention**: components with more than one related file live in their own kebab-case folder containing `<name>.tsx`, optionally `<name>.type.ts` for exported prop types, and a barrel `index.ts` re-exporting the component (and its prop type, when consumed elsewhere) — e.g. `src/components/common/preview-movie-card/`. Single-file components (`logo.tsx`, `rating.tsx`, `genre-list.tsx`) skip the folder. Follow the multi-file pattern once a component needs more than just a `.tsx`.

## 7. State management

There is currently no global client state layer wired into the app:

- `@tanstack/react-query` + `@tanstack/react-query-devtools` are dependencies, and `src/providers/tanstack-provider.tsx` defines a `TanStackProvider` (creates a `QueryClient` via `useState`, `staleTime: 60_000`), but **it is not mounted anywhere** — not in `app/layout.tsx`, not in `BaseLayout`. No component calls `useQuery`/`useMutation`. If you need client-side data fetching/caching, you must first mount `TanStackProvider` around the tree (likely in `app/layout.tsx`, wrapping `BaseLayout` or its children).
- All current data fetching is server-side, inside async Server Components, with no client cache — matching the "no route/no client-fetch yet" stage of the project.
- The only piece of client-side "state" today is local `useState`/`useEffect` inside individual components (mobile menu open/closed, dialog open/closed, header scroll position) — there is no shared/global store (no Context providers besides the unused TanStack one, no Zustand/Redux/Jotai).

## 8. Styling system

- Tailwind v4, configured entirely in CSS (`app/globals.css`) via `@import 'tailwindcss'`, `@import 'tw-animate-css'`, and `@import 'shadcn/tailwind.css'` (the `shadcn` npm package ships its own base stylesheet, used because `components.json` points `tailwind.css` at `app/globals.css` and `config` at `""`). There is no `tailwind.config.ts`.
- Design tokens are CSS custom properties under `:root` (`--primary`, `--secondary`, `--light`, `--dark`, `--danger`, `--success`, `--divider`, etc.), then mapped into Tailwind's theme namespace via `@theme inline { --color-primary: var(--primary); ... }` so they become usable as `bg-primary`, `text-light`, `border-divider`, etc. Fonts are wired the same way: `--font-heading` → `var(--font-dm-serif-display)`, `--font-base` → `var(--font-inter)`, both of which come from `next/font/local` variables declared in `app/fonts.ts` and applied as CSS variable classes on `<html>` in `app/layout.tsx` (alongside a third font, `Geist`, loaded via `next/font/google` but only used for the `--font-sans` variable — `font-sans` is applied on `<html>` but the design system's actual body font is `font-base`/Inter, so Geist's practical effect is minimal).
- Custom utility/base classes (`.container`, `.wrapper`, `.pretitle`, `.card-overlay-gradient`, plus a block of Swiper-specific pagination/arrow overrides) are hand-written in `@layer base`/`@layer utilities` blocks in `globals.css` rather than as Tailwind plugins.
- Component-level variants use `class-variance-authority` (`cva`) + `cn()` (`clsx` + `tailwind-merge`, in `src/lib/utils.ts`) — this is the standard shadcn pattern; follow it for new `ui/` primitives or variant-heavy components.
- Two carousel implementations exist side by side: `swiper` (`src/components/common/swiper-carousel.tsx`, actively used by `SectionListPreview` and `SectionTopRatedMovies`) and `embla-carousel-react` (only pulled in by the shadcn-generated `src/components/ui/carousel.tsx`, which is not exported from `src/components/ui/index.ts` and not referenced anywhere else). Treat `embla-carousel-react`/`ui/carousel.tsx` as dead weight — build new carousels on `SwiperCarousel` for consistency with the rest of the app, or explicitly remove the embla path if cleaning up dependencies.

## 9. Constants & configuration

- `src/constants/pages.constant.ts` — `PAGES` is the single source of truth for internal route paths (`as const`). See the singular/plural convention called out in `CLAUDE.md` (`movie`/`person` = detail prefixes, `movies`/`people` = list routes). Currently only `PAGES.home` ("/") has a matching implemented route.
- `src/constants/api.constant.ts` — `MOVIE_API_URL` (TMDB base URL), `DEFAULT_LANGUAGE` ('en-US'), `API_REQUESTS` (TMDB endpoint path map).
- `src/constants/common.constant.ts` — `IMAGE_URL` (TMDB image CDN base), `PREVIEW_LIST_COUNT` (10, default truncation for list previews), `TOP_RATE_COUNT` (5, used specifically for the hero top-rated carousel), `YOUTUBE_EMBED_URL`, `MOVIE_RATING_CATEGORY` (thresholds used by `getRatingColor` to color-code the star rating: ≥8 success, ≥6 yellow, ≥4 orange, else red).
- `next.config.ts` only configures `images.deviceSizes` and a `remotePatterns` allowlist for `image.tmdb.org` — no other Next.js config (no rewrites, headers, experimental flags, or Turbopack-specific settings) is currently in play.
- Environment: a single `TMDB_API_TOKEN` in `.env` (server-only, not `NEXT_PUBLIC_*`).

## 10. Summary of open issues / things to verify before relying on them

This list consolidates the inconsistencies called out above, for quick scanning:

1. `app/page.tsx` still awaits its two remaining direct calls (`getPopularMovieDetails`, `getTopRatedList`) back-to-back rather than `Promise.all`ing them; every other section's fetch now lives in a sibling self-fetching component instead of one long sequential chain, which is an improvement but not full parallelism — there's still no `<Suspense>` boundary anywhere, so the whole page waits for every block to resolve server-side before anything streams.
2. `TanStackProvider`/React Query is installed but never mounted; no component uses `useQuery`. Don't assume client-side caching exists.
3. `embla-carousel-react` + shadcn's `ui/carousel.tsx` are installed/generated but entirely unused; `swiper` is the carousel library actually in use.
4. `softcore` fields across `Movie`/`MovieDetails`/`TVSeries`/`TVSeriesDetails`/`People` types are not real TMDB fields and aren't consumed anywhere.
5. `TVSeriesDetails.id` is typed `string` but is actually numeric at runtime (TMDB returns a number), unlike `Movie.id`/`TVSeries.id: number`.
6. `@components/*` path alias is declared in `tsconfig.json` but never used (everything imports via `@/components/*`).
7. Prettier's import-order groups reference `@/hooks`, `@/store`, `@/services`, `@/i18n` — none of these folders exist yet.
8.
